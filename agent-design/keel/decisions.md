# Keel: decisions and open questions

What was decided, what it replaced, and what is still open. Part of [Keel](./README.md). Section numbers are shared across Keel's files, so a reference like §7f means the same section everywhere; [the README](./README.md#files) lists which file holds each.

---

## 14. Decisions

Recorded in the decision log below (§14a). In short:

- Mode is not a concept. Plan and implement are sibling templates on a
  shared base, differing by tools, prompt, model and contract, and
  linked by a pipeline (§1).
- One word, one meaning (`taxonomy.md`): completion **checks** (not
  gates), in-run **monitors** (not harness triggers), **agents** for
  the contexts inside a run, and **role** only for RBAC.
- No ledger. The pipeline run is the durable record of work (§7f).
- Ending tools are generated by the harness. A run's tools are one list,
  each marked with how it may be used (`call`, `finish`); the marking is
  the run's configuration, never the tool's server (§5, §5a).
- Keel knows nothing about pull requests. Opening one is an MCP tool,
  on a server that can be bound to the workspace; its result can write
  stage links (§4a, §7g).
- Kinds become tags. Each specialist is its own sub-agent with a scope
  and a grant. Tags only pick which conventions sections go into an
  agent's opening message, for the run and per sub-agent (§3, §4c).
- Outputs split into effects (tools), result, sinks, continuations and
  pipeline edges, by who decides (§7). Every inter-run edge is declared.
- *Revised against the use cases:* saved tool groups carry per-tool visibility and narrowing argument
  overrides (§4b); continuations go back into the same template only,
  and edges between templates belong to pipelines (§7c, §7e); `invoker`
  mints a session delegation for one pipeline run (§8).
- Params never reach prompt text; trust decides where they bind;
  grant-bearing fields take no params (§6).
- MCP tool lists are pinned by snapshot digest per template version
  (§4a).
- Three identities per run; OBO by token exchange; delegation for
  absent users; the R12 confused-deputy rule (§8).
- CEL for every harness expression (§9).

### 14a. Decision log

Kept by the same two rules as Forge's log (`../README.md`, "Maintaining
these documents"): a decision is never edited into a different one, it
is superseded with a new row; and alternatives are recorded, never
invented. Moved here from Forge's README when Keel was named; dates are
when each was decided.

| Decision | Chosen | Rejected alternative(s) | Rationale |

| Platform layering (2026-10-23) | **AgentSpec → Template@version → Run, with Triggers starting runs and Outputs leading from them** ([`README.md`](./README.md) §2); `mode` stops being a field and becomes a template, with `forge.plan` `extends` `forge.implement` | One spec with a `mode` switch inside it; a template language over prompt text | Every way the two Forge modes differ (tools, statuses, report schema, gates) already had its own field, so the switch carried nothing a separate template does not. Published versions are immutable, so "fixed for a run" extends to "fixed for every run of a version" |
| Completion tools (2026-10-23) | **Generated by the harness from contracts** (`completion`, `human.ask_user`, `hatches.handoff`); authors set names, statuses, report schemas and gates, never a `terminal` flag on a tool (`endings.md` §5) | Separate hand-written terminal tools per agent; a `terminal: true` flag any tool may carry | Ending a run is harness behaviour (turn exclusivity, the nudge, gates, cross-checks), and with a flag a remote MCP server's tool would be one annotation away from ending a run and choosing its status |
| Outputs (2026-10-23) | **Four things split by who decides**: effects are tools (the model decides mid-run), the result is the terminal call, sinks are template-declared deliveries, continuations are template-declared edges to more runs or tasks. | Params (2026-10-23) | **Typed, structural placeholders whose `trust` decides where they bind**: `external` and `principal` text binds to envelope inputs only, `config` params bind to config slots and must declare a ceiling, and grant-bearing fields take no params (`run-spec.md` §6, rule R4) | String interpolation into the spec or prompt; untyped params | Params can then narrow and never widen, and because they never reach prompt text every run of a version shares one cacheable prefix |
| Tool snapshots (2026-10-23) | **A template version pins each MCP server's `tools/list` by digest; a changed input schema or annotation refuses the run** (`../tools.md` §4a) | Trusting the live list at run start | A server redeploy would otherwise change a published, reviewed template's tool surface with nobody publishing anything |
| On-behalf-of (2026-10-23) | **Three identities per run (principal, requested_by, actor); OBO by per-call token exchange; a stored, versioned, revocable `Delegation` for absent users; and no write tool on a service credential in a user-runnable template without a harness entitlement check** (`authority.md` §8, rule R12) | Service credentials everywhere; running event-triggered work as whoever caused the event | A service credential in a user-run template is a confused deputy, and mapping an event's author to an account says who they are, not that they consented |
| Tier→model map (2026-10-23) | **In a `Deployment` resource, with provider capabilities and the global ceiling** — closes `../models.md` §10's first open point | In each template | The same template version should run on Bedrock and the Anthropic API without a new version |
| Finishers (2026-10-23, revised against use cases) | **A template may name real tools or harness actions as its endings** (`completion.finishers`, `complete: false` to drop the generic `Complete`): the harness generates a separate tool per finisher, runs the completion gates before the action, and returns a failed action to the model ("completion gates" are now called completion checks, see the vocabulary row below); `open_pull_request` and `request_help` are the two harness actions (`endings.md` §5a). **Narrows** the *Completion tools* row above: termination is still never a property of a tool, but the author now chooses which actions end a run | A `terminal` flag on the tool (rejected in that row, for the same reasons); keeping `Complete` the only ending and doing Jira/PR updates as sinks | The use case is the model choosing *how* to end (open a PR, or just update the ticket, or hand to a person), which a fixed sink cannot express. Marking the ending in the contract rather than on the tool keeps every reason the earlier row gave, and running gates before the action is what makes an irreversible ending safe |
| Cross-template edges (2026-10-23, revised against use cases) | **A template's continuations go back into the same template only; edges between templates live in a versioned `Pipeline`, with its own sinks** (`outputs.md` §7c, §7e). **Supersedes** the part of the *Outputs* row above that made plan → implement, HandOff landings and review → fix template continuations | Template continuations naming any template (that row as first written) | `forge.plan` hard-wired `forge.implement`, and "update Jira when the pipeline ends" had nowhere to live except a template that is also run on its own. Pipelines are a path, not a workflow engine: no loops, branches or joins |
| Saved tool groups (2026-10-23, revised against use cases) | **A versioned `SavedToolGroup` with per-tool visibility and argument overrides that only narrow**: describe, default, require, restrict, or fix and hide; renaming an argument is not supported (`../tools.md` §4b, rule R13) | Inline groups only; overrides that can widen or rename | Narrowing is what makes the overrides safe to hand to group authors, and checking them against the pinned snapshot makes "narrow" checkable rather than a convention |
| Invoker sessions (2026-10-23, revised against use cases) | **A chat or UI request runs as the invoking user through a session delegation minted for that one pipeline run** (`authority.md` §8) | Requiring a stored delegation for every chat user; running later stages as the service | A cheap stage that hands off may finish after the chat request returns, and the stronger stage must still query as the user, not as the bot |
| Ad-hoc runs (2026-10-23, revised against use cases) | **An unsaved spec is published as a content-addressed `adhoc.<digest>` version and checked by every rule before it runs** (`run-spec.md` §6) | Running an unvalidated inline spec | "Pick a group, a prompt and a repo and go" should not be a way around the publish rules |
| Mode (2026-10-23, on review) | **Not a concept.** Plan and implement are sibling templates on a shared, non-runnable base (`forge.coding`, `runnable: false`), each with its own grant, prompt, model and completion contract, and linked only by a pipeline (`keel/README.md` §1). **Supersedes** the *Platform layering* row's "`forge.plan` `extends` `forge.implement`" | Plan as a variant of implement (that row); a `mode` field or `<mode>` envelope tag | A run's behaviour should follow from what it was given, not from a label that can disagree with its tools. Extending one from the other read as exactly such a label |
| Vocabulary (2026-10-23, on review) | **One meaning per word, recorded in [`taxonomy.md`](./taxonomy.md)**. Three platform renames made at once: completion gates → **completion checks** (gate means a human wait), harness triggers → **monitors** (trigger means what starts work), ledger `owner` → **concurrency key**. Three older collisions (`handoff`, `Task`, `role`) are listed there with recommendations, not renamed | Leaving the overlaps to context | Each pair is used near the other in the same documents (a finisher runs completion checks and can open a gate), so context doesn't disambiguate them |
| No ledger (2026-10-23, on review) | **The pipeline run is the durable record of work; every run belongs to one**, and a template run on its own is a one-stage pipeline run. Stage records carry the ledger's jobs: attempts and a retry policy, `waiting_on`, a `settle` wait on the PR (the ledger's `handoff`), spinoffs as child pipeline runs, concurrency held while settling, health queries, the caps (`pipelines.md` §7f). **Supersedes** the ledger as a mechanism (`../orchestration.md`, and the ledger rows above from *The layer above a run* through *Reopening an abandoned ticket*); their rules are kept and mapped in §7f's table | Keeping a ledger beside pipelines, with a pipeline run deciding which stage is next and a task deciding whether and when it runs | Two durable stores with overlapping states (waiting/parked, running) would have had to agree, and the examples already showed the seam: a trigger "creating a task" for a pipeline had no defined meaning. Folding the ledger in also moved the end-of-work Jira update to when the PR merges, rather than when the agent stops |
| Role means RBAC (2026-10-23, on review) | **"Role" means only an RBAC role** (a set of permission groups, assigned to a team, held by its members), which lives outside this spec. The contexts inside a run are **agents** (orchestrator, sub-agents); the run-level spec is renamed `RunSpec`; the spawn argument is `kind`; the platform names the permissions it checks (`authority.md` §12a) | Keeping `roles` for the orchestrator and sub-agents | The deployment has an RBAC system where role already means something, and permissions sit right next to agents in every authority discussion, so the two senses would meet in the same sentences |
| Name and layout (2026-10-23, on review) | **The platform is named Keel; its docs live in `agent-design/keel/`, split by area with section numbers shared across files, and Forge's configuration lives in `agent-design/forge-on-keel/`**. Keel's own decisions and taxonomy move with it | The names Anvil and Plinth; a top-level folder beside `agent-design/` | A name stops "the platform" and "Forge" blurring in every sentence. Anvil pairs with Forge but reads as coding-flavoured, which is the line the split exists to draw. Keeping the folder inside `agent-design/` was the owner's call, trading a cleaner separation for less movement |
| One vocabulary (2026-10-23, on review) | **Keel owns one shared vocabulary of integrations and capabilities (events, channels, harness actions, input builders, checks, monitor signals); use cases never extend it.** A name says what it integrates, not which use case first needed it (the PR-diff builder was renamed from `review_diff` to `pr_diff`). Forge is a set of use cases and their configurations, not an extension of Keel | Per-deployment registered catalogues, with Forge's vocabulary as one pack among several (proposed in this session, not adopted) | The same tools, events and actions serve Forge and data-analysis use cases alike, and pipelines mix them. Per-use-case vocabularies would make that mixing a matter of reconciling packs, and would hide shared integrations behind use-case names |
| Template stage defaults (2026-10-23, interview) | **A template may declare `stage_defaults` (`retry`, `settle`), used when it runs alone or when a pipeline stage leaves them unset; a stage's own value replaces the default as a whole** (`pipelines.md` §7f) | Retry and settle on pipeline stages only | A template that opens a PR should wait for the merge without being wrapped in a pipeline just for that |
| Late approvals (2026-10-23, interview) | **A gate answered after the requester's session has ended does not revive it: acting for the user then needs their stored delegation, or the edge refuses with `delegation_missing` and the stage blocks** (`authority.md` §8) | Running the follow-up as the approver (the recommendation put to the owner); minting a stored delegation at the start of every user-started run | Authority stays with the person the work is for or with the service identity, never with whoever clicked approve; and no standing consent is created that the user never asked for |
| Retrying `failed` (2026-10-23, interview) | **Not retried by default**; retries cover running out of budget, infrastructure failure and a lost lease, and a genuine failure blocks the stage for a human. Templates and stages may opt in | Retrying a failure once by default | The ledger's original reasoning holds: more of the same rarely fixes a real failure, and an attempt spent on it is lost to a budget retry |
| Scope limits (2026-10-23, interview) | **Pipelines are paths (no loops, parallel branches or joins) and harness expressions are CEL**, confirmed | Branching pipelines; a different expression language | Fan-out already lives inside a run; CEL is typed, bounded in cost, and can't loop |
| Policy defaults (2026-10-23, interview) | **Gate expiry 7 days, then block the stage; session delegation cap 24 hours; `stranded` after 1 hour, `waiting_stale` after 3 days**, as deployment `defaults.policy`, overridable where a template or pipeline has a field | Gate expiry of 14 days or none; abandoning on expiry; a session cap of 1 or 8 hours (8 was recommended); stale thresholds of 15 min / 1 day or 4 h / 7 days | A week covers an absence without letting stale questions pile up; blocking keeps work someone forgot to answer. 24 hours lets a long report or an overnight stage finish under the user's authority |
| Rendering (2026-10-23) | **The system prompt holds only what is fixed per template version (base text and the capabilities block); per-run generated blocks and the inputs go into the opening user message; mid-run changes are appended as messages. Prompt text has no placeholders** (`run-spec.md` §3) | Forge's original layout, with `{{ENV_BLOCK}}` and `{{TASK_ENVELOPE}}` inside the system prompt | §6's claim that every run of a version shares one cached prefix was false with per-run blocks in the system prompt. Anthropic's harness guidance gives the same shape: freeze the rendered prompt, announce per-session facts in the first user turn, send deltas |
| Registry manifests and report schemas (2026-10-23) | **A configuration folder lists its prompt and report-schema refs in `registry.json`; each resolves to a file, or to a design document's section while the text is still being designed there (R16).** Forge's report shapes are extracted to `../forge-on-keel/reports/`; the plan report gains `write_scope`; the analysis answer and document schemas are new, with every figure a claim carrying refs | Leaving refs unresolved names; duplicating every prompt into a file at once | Refs that resolve to nothing can't be published or checked. Pointing at a document section keeps one copy of text that is still changing |
| Bulk re-publish (2026-10-23) | **`GET /v1/dependents` and `POST /v1/dependents:republish`**: draft each dependent with only the one reference moved, run every rule, optionally publish, optionally cascade through extends and pipelines; each dependent succeeds or fails alone | Templates following a group's latest version automatically | Automatic following would change published, reviewed templates without anyone publishing them, the same reason tool snapshots are pinned |
| Draft runs (2026-10-23) | **Drafts run only on a sandbox deployment, as the caller, with sinks and actions recorded rather than delivered and MCP writes denied unless the sandbox allows them; deployments become a list** (`triggers-and-runs.md` §10a) | Drafts limited to `dry_run`; a "test mode" flag on production | Eval needs real runs of unpublished changes; a separate deployment keeps tier maps and servers apart, and a flag on production would put test effects one setting away from real ones |
| Hidden-tool reveal on Anthropic (2026-10-23) | **Verified as supported: mid-conversation tool changes reveal a `defer_loading` tool through an appended system message without breaking the cache.** Recorded per provider (`reveal`) and per tier (`supports_reveal`); unsupported cases resolve `hidden` to `deferred` or `loaded` | Treating `hidden` as `deferred` on Anthropic (the previous assumption) | The beta covers the current Opus, Fable and Sonnet 5.5 models on the Claude API, AWS, Bedrock and Vertex. Sonnet 5 and Foundry are the gaps |
| Kind scope (2026-10-23) | **`kind_scope` on a sub-agent: per-kind scope text rendered into its opening message as a `<lens>` block** | A prompt version per lens; prompt slots filled per spawn | Keel's kinds were declared to have three payloads (context sections, prompt scope, tool grants), and only the tool grant had a field. Putting the scope in the opening message keeps one cached system prompt per sub-agent, consistent with the rendering rule |
| Tool use marking (2026-10-23, interview) | **A run's tools are one list, and each entry says how the agent may use it: `call`, `finish` or both, with a `finish` block giving the ending's status and report.** Keel's built-ins may allow only some uses (`RequestHelp` is finish-only). Ending tools take the tool's arguments flat, with `summary` and `report` reserved (R14). **Supersedes** the *Finishers* row: the separate `completion.finishers` list goes, and so do nested `args` | A separate finishers list (that row); nested `args` | The owner's model: one tool list, each tool marked with how it may be used when the run starts. The marking is still the run's configuration, never the tool's server, so every reason the *Completion tools* row gave still holds. Flat arguments are simpler for the model to emit; reserving two names is a small price |
| No pull requests in Keel (2026-10-23, interview) | **Keel has no PR concept and no harness actions.** Opening a PR is an MCP tool (e.g. `mcp:scm/open_pull_request`) granted mid-run, as an ending, or called by a pipeline sink. Two generic mechanisms replace what the action did: an MCP server can be **bound to the workspace**, and a tool's result can write **stage links** for the settle wait. `workspace.git_writes`, R15 and the PR-specific P9 go; P9 now covers any workspace-bound sink. **Supersedes** the *Finishers* row's harness actions and the first version of `outputs.md` §7g | Harness actions (`action/open_pull_request`) owned by Keel | A platform that knows about PRs is a platform shaped by its first use case. Binding a server to the checkout keeps the push supervised by a declared, pinned, credentialed tool, and the model's `Bash` still can't push |
| No kinds (2026-10-23, interview) | **Keel drops kinds.** Each specialist is its own sub-agent definition with a `scope` (rendered as a `<scope>` block) and its own grant; conventions narrowing is `context.conventions.topics`. `spawn_kinds`, `kind_grants` and `kind_scope` go. **Supersedes** the *Kind scope* row, and Keel's use of Forge's "kinds: one vocabulary, three resolutions" (`../context-files.md`), which stays as Forge's history | Keeping kinds, with kind_scope (that row) | One word did three jobs at spawn time, and the owner found it hard to explain; each job already had a plainer home in sub-agent definitions, tool groups and context tags |
| Kinds are tags (2026-10-23, owner) | **What survives of kinds is tags.** `context.conventions.tags` (was `topics`) narrows the run's conventions; a sub-agent's `conventions: {tags}` gives it its own `<conventions>` block after its `<scope>`, so a spawner no longer copies conventions text into briefs. Tags are set by the template, never by a spawner or an agent, and are not bindable on a sub-agent; they select context and never a tool or a grant. Absent or empty tags mean the whole corpus; policy and untagged sections come back regardless; an unknown tag is a resolution error (`../context-files.md` "Kinds"). A spinoff carries `tags` for the run it starts. R17 checks a sub-agent's block has a `context.conventions` to resolve with. **Refines** *No kinds* | A `kinds` field doing prompt scope, tools and context at once (that row's rejected option); tags selecting prompt fragments too | The owner's reading: kinds were mostly tags for context and prompt construction. Keeping the tag and dropping its other two jobs keeps what was useful (per-specialist conventions) without a tag ever widening authority. Prompt text stays explicit in `scope`, so the rendered message is readable from the template alone |
| Lens (2026-10-23, interview) | **The data-analysis use cases are a separate set named Lens** (`../lens-on-keel/`, templates `lens.*`), not part of Forge. "Lens" as Forge's word for a review specialism is retired across the design docs in favour of "specialist" | Analysis as part of Forge (as `../data.md` had it) | The tools are shared across use cases, not owned by Forge, so analysis shouldn't sit inside Forge's configuration |
| Registry files only (2026-10-23, interview) | **Every registry entry is a file.** **Supersedes** the part of the *Registry manifests* row that allowed a design document's section | Document sections for prompts still being drafted | One copy of each text, and it's the one that ships |
| Interrupted attempts (2026-10-26, weekly pass) | **A retry after `infra_failure` or a lost lease carries a harness-written `interrupted_attempt` block (calls in flight, last calls, death signal, workspace `retained`/`fresh`) and a fixed paragraph telling the model to check each in-flight call before reissuing it and to do the work another way if it could have killed the runner; two consecutive deaths on the same tool and arguments digest block the stage with `repeated_infra_failure`** (`pipelines.md` §7f) | A blind retry with an empty `prior_attempt` (the previous behaviour); resuming the dead attempt's transcript as Goose and Claude Code do | Keel retries are fresh attempts by design, so the transcript is not available to resume, but the event stream already holds the facts. Claude Code 2.1.309 is the one source that tells the model the call in flight may have caused the death (`../../agent-run-recovery.md`) |
| Approval inputs (2026-10-26, weekly pass) | **An `approve` question binds to a digest of its `action` and the bytes of its `staged_paths`; the execute run re-hashes first and ends with `approval_inputs_changed` on any difference, and the question is asked again** (`../formats.md` §5, `../tools.md` `AskUser`) | Passing `staged_paths` as a list with no binding (2026-10-19) | The plan gate already binds to a hash (§5a rule 4); the auto-mode red-team measured approve-then-overwrite at 43–72% against unmonitored edits (`../../agent-permissions-approval.md` §2d) |
| Sub-agent reports (2026-10-26, weekly pass) | **A `Task` result is a nonce-wrapped `<subagent_report>` with the lowest trust of what the sub-agent read; facts may be used, instructions and approval or scope claims are never followed** (`tools-and-agents.md` §4c). **Supersedes** `../tools.md`'s note that `general-purpose` reports "should generally be trusted" | Trusting research reports (the old note); escaping report text like OpenClaw (rejected: reports are read closely, and the nonce already makes the boundary unforgeable) | Handoffs between contexts were a working attack channel in the red-team (18/18 against auto mode, 0/20 against the hardened Auto Mode ++), and every Forge delegate reads untrusted input |
| Git metadata under a bound server (2026-10-26, weekly pass) | **The sandbox mounts the git directory read-only; the workspace-bound server owns the only writable copy and runs git with hooks and fsmonitor off, `include` ignored, a protocol allowlist and credentials through a helper** (`tools-and-agents.md` §4a) | Relying on `Bash` being denied git writes (the previous text) | `Bash` can write `.git/config` and hooks without running git, and the server pushes with deployment credentials outside the sandbox. Claude Code 2.1.309–2.1.310 treats a sandbox-writable git folder as untrustworthy for the same reason (`../../agent-git-vcs.md` §8) |
