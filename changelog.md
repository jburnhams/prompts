## 2026-09-20

Followed the data-analysis pass with the question it raised but did not answer: **if the harness is already TypeScript, can the data tools be TypeScript too — and does the computation still need a server?** Yes and no. Three sources read, two new folders, one new root doc. The design fold is deliberately not written yet.

- `agent-local-compute.md` — new, 8 sections. Opens by separating three decisions that usually get made as one: *where the bytes are scanned*, *what language the engine is written in*, and *what the model emits*. The pass is about the combination the Python world cannot reach — an engine in the harness's own language, moved to wherever the data is, with the model's tool surface unchanged between deployments
- **The idea is already shipped.** `data-agents/hyperparam/` — new: a pure-JS data stack (squirreling ~13 KB with **zero dependencies**, hyparquet ~9.7 KB gz, icebird, hyparquet-writer, hightable), MIT throughout, described by its own authors as built for "browsers, Electron, Node, agent sandboxes", with a paper behind it (*A Query Engine for the Agents*, arXiv:2605.27785, May 2026) and **`squirreling-mcp` wrapping the same engine as an MCP server**. Three tool definitions captured verbatim
- **§2's claim is that the pure-JS-versus-WASM gap is architectural, not tuning.** Cold start 0.6 s against DuckDB-WASM's 19 s is a property of shipping 70 KB of JS rather than instantiating a multi-megabyte module. The load-bearing half is the async one: a vectorized WASM engine **cannot** host an `await` inside a scalar UDF, because "scalar UDF calls still cross the WASM boundary synchronously from the engine's perspective" — so `SELECT llm('classify', content) FROM traces LIMIT 5` making **exactly five API calls** is available to an AsyncGenerator engine and structurally unavailable to a compiled one. The cost and throughput figures (3× cost, 300×/192× speedups) are **vendor-run by the author of the libraries measured, with no independent replication found**, and are flagged as such in three places. The fair counter-statement is also recorded: DuckDB-WASM is a far more complete analytical engine, and for a long-lived local workload the trade reverses
- **Verified rather than repeated**: `grep -rn "new Function\|eval(" squirreling/src` returns nothing — the only `import(` hits are JSDoc annotations. The engine parses SQL to an AST and interprets it, so **model-written SQL never becomes JavaScript**. Contrast `data-agents/arquero/` — also new — where verb expressions are AST-verified against a closed `op.*` vocabulary (the `ERROR_CLOSURE` / `ERROR_ESCAPE` constants are the spec) and *then compiled*, which rests on the completeness of a verifier rather than on the absence of an interpreter
- `code-mode/` — new top-level category. **Code Mode has converged from four directions and the collection now covers all four**: Cloudflare (read from source here), Anthropic's published pattern, Codex `tool_mode: "code_mode_only"` (already in `codex/`), DeepSeek (already in `deepseek-harness/`). The two discovery answers turn out to be one idea bound to different substrates — Anthropic's filesystem of `.ts` wrappers makes **the tool catalogue a repository** a coding agent already knows how to read; Cloudflare's `search()`/`describe()` is what you use in a browser, where there is no filesystem
- **Cloudflare ships a browser executor**, which is the find. ~200 lines, zero dependencies, MIT: `sandbox="allow-scripts"` with *no* `allow-same-origin` (opaque origin), `default-src 'none'` in a CSP `<meta>` injected into the `srcdoc` (which kills `connect-src` with it), `postMessage` with a per-execution nonce checked both ways, and providers passed as **function parameters rather than globals** so a program cannot enumerate `globalThis` for capabilities it was not handed. Its own docs name the gap: a timeout "cannot preempt tight synchronous loops like `while (true) {}` because those block the browser event loop"
- **§4 re-derives the sandbox question under a blast-radius threat model** — the model is careless, not hostile — and gets a different answer from the adversarial literature: five tiers, with the iframe+CSP executor as the sweet spot and a Worker-inside-the-iframe as the fix for the hang. Recorded alongside: a Web Worker is **not** a network boundary (it has `fetch`), ShadowRealm is Stage 2.7 and not a security boundary anyway, and `node:vm` is not a sandbox
- **The cheapest control in the pass is not a sandbox.** `squirreling-mcp` parses and *plans* the SQL, then walks the plan for scan nodes to resolve `FROM`-clause identifiers — so what a query will touch is known before a byte is read. That is where an allowlist, a cost estimate or an approval prompt belongs; a regex over the query text would not do it, and a sandbox does not help, because the expensive query is authorised
- **§5, the fork worth arguing about: SQL-as-data or JS-as-code.** The seam is already in the engine contract — a UDF is *registered by the harness and merely named by the model*, so the capability surface inside the query language needs no sandbox at all, because no model-authored code runs. Which also makes an `llm()` UDF a **governance** question: laziness makes `LIMIT 5` genuinely five calls and does nothing about the unbounded case, where the query costing $4,000 is textually indistinguishable from the one costing $0.004
- **Two contracts worth stealing outright**, both about forty lines of type: `AsyncDataSource`/`ScanOptions`/`ScanResults` as the resolver interface `agent-design/data.md` §2a specified abstractly, and its two honest pushdown booleans (`appliedWhere`, `appliedLimitOffset`) — a Parquet source pushes projection, a CSV source pushes nothing, a Postgres source pushes everything, same interface, saying what it actually did each time
- **§7 on what breaks when compute moves into the tab**, where the finding is that a good engine does not give you a good result contract for free: squirreling streams, and `squirreling-mcp` calls `collect()` to materialise 40,000 rows in order to show 100 of them, then reports `... and 40922 more rows` with no cursor, no offset and no ref. The sharpest conflict with the existing design is that **artifacts become tab-local and mortal** while the hands-off completion gate (`data.md` §2f) needs refs that resolve
- One correction to the previous pass: `agent-data-analysis.md` §12 listed streaming partial results as unsolved and blamed the harnesses. The engines *do* stream — `rows()` is an `AsyncGenerator` — and MCP has no result streaming or pagination to carry it. The gap is in the transport, not the compute
- `code-mode/webmcp.md` — `navigator.modelContext`, recorded with its status stated plainly: a W3C **Community Group** report, Chrome-only behind a flag, and an adapter whose own header reads "DO NOT USE IN PRODUCTION … WILL break between releases". Noted that "the page can register tools" is also the threat model, and that an agent already running its own loop in the page can simply call the functions
- `README.md`, `sources.md` — the new category, the topic-doc entry, two source-table rows, and a fetch table with per-file paths plus the `grep` that checks the no-codegen claim
- `cloudflare-agents/` — new, and a different *kind* of source: every other harness here is a **process**, this one is a **Durable Object**. Four files. The headline is `agents/context`, which assembles the system prompt from labelled blocks where **the provider's shape decides both the rendering and the tool surface** — `get()` is read-only text, `+set()` adds `set_context`, `+search()` renders a summary and adds `search_context`, and *"the checks are structural, not nominal"*, so **an agent with only read-only blocks gets no tools at all**. Nothing else in the collection derives prompt and tools from one declaration. `getSystemPrompt()` is now *"the legacy fallback"*, with a runtime warning telling you to move to `configureContext()` — the third independent arrival at *the monolithic system prompt is not the unit of composition*, after OpenClaw's per-surface assembly and Codex's diff stream
- **A third answer to prefix-cache stability, and the only one that survives the process dying**: `freezeSystemPrompt()` renders once and **persists the rendered bytes**, so *"a cold wake reuses the exact prompt string the model already cached instead of re-rendering a subtly different one"*. The stated trade is recorded too — `setBlock()` deliberately does not update the frozen prompt, so a block written mid-session is invisible until an explicit refresh
- **Eviction as a numbered hazard** (~70–140 s inactivity; code updates **1–2× a day**, non-deterministic; 15 min alarm cap), with the consequence spelled out — the upstream HTTP connection to the LLM provider *"is severed permanently"* — and two mechanisms whose difference is one line: *"`keepAlive()` reduces the chance of eviction. `runFiber()` makes eviction survivable."* Checkpointing is explicit (`ctx.stash()`) and recovery is a handler the author writes, which is more work and more honest than promising deterministic replay
- **Compaction as a non-destructive read-time overlay** — originals stay, the overlay applies on read, so it is reversible, auditable and branch-local on a message *tree*. Gated on an O(1) token aggregate stamped at write time, so the trigger *"never reads the transcript to decide whether to compact"*. It **fails open** where OpenClaw's fails closed, and the doc records why that is consistent rather than contradictory: non-destructive storage is what buys the right to fail open. Also the rule most hand-rolled compactors get wrong, stated as spec: boundaries aligned so *"a tool call is never separated from its result"*
- **Recovery-aware delivery**, which has no equivalent in the collection: restart before streaming starts → replay the answer; restart after → post an interruption notice rather than risk a duplicate partial. Whether a retry is safe depends on whether a human already saw the output, which is not something an idempotency key can tell you
- **Dynamic agents (facets)** as the far end of the sub-agent axis `agent-subagent-architectures.md` catalogues — children with their own isolate and their own SQLite, reachable only through the parent, with `abort` (storage survives for inspection) separated from `delete` (wipes it). Plus agent tools, which present a sub-agent to the model as an ordinary tool while giving the *user* a replayable child timeline and a drill-in URL
- **Six human-in-the-loop patterns with the vendor's own decision tree**, and the finding that **exactly zero of them compose with Code Mode** — Cloudflare excludes `needsApproval` tools from codemode rather than pausing mid-program. An SDK with six approval patterns having none that work inside a generated program is the clearest evidence yet that program-shaped tool use and human-in-the-loop are an unsolved combination, not one vendor's gap
- `code-mode/cloudflare.md` stays as the Code Mode slice and now points at the wider read; **WebMCP is confirmed as first covered in this pass** — the earlier grep hit was `modelcontextprotocol` matching `modelContext` case-insensitively
- `code-mode/webmcp.md` — rewritten as an explicit **PARKED** placeholder rather than a research note, so the question is not re-opened from scratch. Three sentences of what it is, four reasons it is not useful here (it solves a *browsing* problem, not an internal-tooling one; an agent already running its own loop in the page can just call the functions; it is one engine behind a flag under a Community Group report, not a Recommendation; and "the page can register tools" is also the threat model), the one pattern worth borrowing without it (`AbortSignal`-scoped registration), and **three named re-check triggers** — the load-bearing one being "we need an agent to drive third-party pages"

## 2026-09-12

Opened a fifth source category and the research pass behind it: **agents whose task is answering a question about data**, not editing a repository. Thirteen harnesses read from source into `data-agents/`. The framing that made it worth doing: a data agent is not a coding agent with pandas in the prompt — four things change together (the work product has to be *rendered* by something; the interesting state lives in a process the agent cannot see; the data never fits, so every read is a projection; and running it successfully proves nothing).

- `agent-data-analysis.md` — new, 12 sections. **§1 records two pieces of ecological context that frame everything else**: Open Interpreter's `main` is now a Rust, Codex-derived *coding* agent (the Python interpreter last shipped in `v0.4.2`, 2024-10-24), and Positron Assistant has left Posit's OSS tree, leaving only the call site `positron.ai.generateAssistantPrompt(request)`. Both moved away from open data-analysis agents in the same window that Microsoft Research, Datalayer, E2B, marimo and MathWorks shipped readable *substrate* — which is the layer a framework wants to consume anyway
- **The headline is a four-way convergence nobody names**: jupyter-mcp's `execute_code` vs `insert_execute_code_cell`, marimo's scratchpad vs `cm.get_context()`, Data Formulator's "inspection tools" vs "actions", and the claude.ai container's `/home/claude` vs `/mnt/user-data/outputs` are **the same boundary** — probe freely and invisibly, commit deliberately and visibly — enforced twice by mechanism and twice by a sentence. The jupyter-mcp sentence ("Under no circumstances should you use this tool to … perform variable assignments that affect subsequent Notebook execution") turns out to be about **reproducibility, not safety**: a notebook whose state was established off-document is a lie
- **§3 is the pass's centre** — the stateful/stateless fork, and the finding that the prompts have to follow the mechanism. Open Interpreter: "it's critical not to try to do everything in one code block." Data Formulator: "combine related steps into a single script." Both correct; a harness that changes one without the other gets silent `NameError`s. Tabulates the only four known answers to the problem a persistent kernel creates — the agent's transcript and the kernel's namespace diverge and *the agent cannot see the divergence* — including MetaGPT's expensive one (**prompt a second model call to write a probe cell, run it, inject its output**), which is the only one that works when the harness cannot introspect the runtime
- **§7, who draws the chart** — the full spectrum, from free code through **LIDA's under-used scaffold** (the model completes `<imports>` and `<stub>`; the signature, the data variable, the title, the return value and the `chart = plot(data)` line are unbreakable) to Data Formulator banning matplotlib, plotly and seaborn from the sandbox outright. Adds the answer this collection had been circling: **E2B's two custom Jupyter MIME types** — `e2b/data` (a DataFrame as columns) and `e2b/chart`, a matplotlib `Figure` *deconstructed back into data* with title, axis labels, units parsed out of the label by regex, tick positions, scale type and every plotted point with its series label. Set against marimo's `ctx.screenshot()` (headless Chromium, 2× DPI, against the live notebook) the two are complements: one tells you what the numbers were, the other whether the legend collided
- **§11 checks the "MCP can't do binaries" premise against the spec** (`2025-06-18`) and finds it not quite right — embedded resources carry base64 `blob`s, which is exactly the wrong thing to do for a parquet file. The right primitive is `resource_link`, and **jupyter-mcp already ships the whole ref-with-metadata pattern inside plain MCP**: cells and *individual outputs* as resources (`notebook://{name}/cells/{id}/outputs/{i}`), outputs listed rather than inlined, cache TTLs on the protocol's own `_meta` key, `audience` annotations separating the bytes from the preview, and the clearest statement of the principle in the collection ("A cell that printed a megabyte otherwise spends a megabyte of context every time anybody reads it"). §11c then says what a **table** ref needs that a blob ref doesn't — schema, exact row count, preview, format, provenance, and *relational* rather than byte-range operations
- `data-agents/` — new folder, 13 sources with verbatim prompt and tool text: `open-interpreter/` (the `v0.4.2` archetype, with the `##active_line` rewrite the R backend needs and the dead `add_scrollbars` path whose comment explains why paging requires the harness to keep what it elided), `jupyter-mcp/`, `data-formulator/`, `marimo/`, `vanna/`, `metagpt-di/`, `lida/`, `e2b/`, `pandasai/`, `postgres-mcp/`, `matlab-mcp/`, `btw/`, `positron/`
- Individually worth the read: **btw's four named projections of a data frame** with the best statement anywhere of what "show me the data" means (column summaries answer *what is in this table* in O(columns); rows answer *what does a record look like* and are needed rarely) and `run_r` **disabled by default** with the absence of a sandbox documented rather than glossed; **Vanna's `run_sql`**, which writes a CSV, hands the model a 1,000-character preview *plus* the filename *plus* an instruction **not** to summarise it, and hands the UI a `DataFrameComponent` with a text fallback — four projections of one call; **Positron's `convert_to_code`**, which turns a grid's filter/sort state into pandas, polars, data.table or dplyr and is the missing piece in every "chat with a dashboard" design, alongside special-value integer codes (`NULL: 0, NA: 1, NaN: 2, NaT: 3, None: 4, ±INF: 10/11`) that nobody else has; **Postgres MCP** changing its *tool description and MCP annotations*, not just its driver, between access modes, and validating with a `pglast` allowlist of statement node types **and functions** (because `SELECT pg_read_file('/etc/passwd')` is a perfectly good `SelectStmt`); **MATLAB MCP** factoring the four annotation flags into four named constructors with the consequence of misuse in the comment ("the read-only hint tells hosts they may skip user confirmation, so misusing it lets writes through silently"); and **Data Formulator's `addaudithook` sandbox**, whose load-bearing trick is pre-importing every allowed library *before* arming the hook
- `agent-design/data.md` — new. **Zero new tools**, which is what the ref system bought: a table is a thing at a ref, profiling it is a read, querying it is a read with a selector, charting it is a validating write. Six v1 adoptions — a **`table://` scheme**; a **`table` artifact kind** whose stub defaults to column summaries (btw's distinction, adopted) and **always states null counts, even when zero**; **`:rows:`/`:cols:`/`:sql:` selectors**, with `:sql:` defended as the *reducing* operation a relation needs (`artifacts.md` §5.4's own criterion — "a handle whose only operation is 'load it all back' is a deferral"); **tabular spills minting `table://`** so a 400k-row result stays queryable rather than line-addressable; a **chart-spec validating write path** with a four-code refusal vocabulary (`spec_invalid`, `unknown_field`, `no_data_ref`, `type_mismatch`), which catches at write time the commonest chart bug; and a **provenance half for the completion gate** (every `table://` in the evidence must have a `produced_by` that resolves), closing the open problem no source in the pass fills
- **The probe/commit rule** (`data.md` §1) joins the structured-representation rule as a design-wide rule stated once. Read against the existing surface, Forge implements it everywhere except `Bash` — `python analyse.py > /dev/null` and `python post_to_the_pr.py` are the same call shape. Also: a **third entrypoint**, `analyse`, with modes `explore` and `answer`, separate from coding for the same reason review is — not a different tool surface, a different *completion contract*
- **Five rejections, including the two that look most obviously right**: a `Describe` tool (subsumed — `Read` is already a converting reader, and a profile is what reading a relation should produce; it fails the design's own granularity rule on three of four counts) and a `Chart` tool (subsumed — in Forge a chart is written and then cited, and `generative.md` §2a already made comment bodies accept refs). Plus Data Formulator's 30-type chart vocabulary (Vega-Lite already has a schema), MetaGPT's per-task-type guidance fragments (genuinely good, and the second half of a skill mechanism whose first half `generative.md` §2e defers — the strongest argument in the pass *for* building it), and LIDA's personas. Positron's special-value codes are **adopted in spirit rather than literally**: null counts in the stub, where the information actually changes a decision
- One narrowing recorded rather than edited in place: `artifacts.md` §4a's "a read carrying a selector never spills" gains a `:sql:` exception, because a query result is a new ref and is subject to §4 like any other
- `README.md`, `agent-design/README.md`, `sources.md` — the new category, the reading-order entry, the entrypoint diagram, and the fetch table with per-file paths (including the warning to clone Open Interpreter's **tag**, not `main`)

Turned the generative-output research into design work. The framing that made it worth doing: Forge makes no pictures, so the transferable material is not about drawing — it is about **the boundary between what the model authors and what the harness renders**, which this design crosses in four places it was improvising (`AddComment`'s body, `Complete`'s report, `AskUser`'s question, and the suggestion-block fallback).

- `agent-design/generative.md` — new. Five v1 adoptions, **none of them a new tool** (the surface stays at 11), under a stated admission rule: an item earns a place only if it changes a contract the design already has. §1 names the rule the whole pass reduces to — **emit the most structured representation the destination can actually hold, and where it can't, degrade one step and say so** — and then shows the design was already implementing it four separate times (suggestion fallback, anchor fallback, finding schema, plan schema) without knowing they were instances of anything, which is why it now lives once in `formats.md` §8 with back-references rather than four times
- **`AddComment` gains `body_ref`** (§2a) — a write-side ref through `artifacts.md`'s existing closed scheme set, `oneOf` with `body`. `artifacts.md`'s "bytes never enter context" rule was stated only for *reads*; `ArtifactData`'s `data`-or-`file_path` pair is the worked precedent, described in its own schema as existing "so a large document need not pass through the conversation". Four constraints, all inherited rather than invented: no new scheme (the closed set is the whole security argument), echo the resolved ref and byte size, **`suggestion: true` forbids `body_ref`** schema-side (a block that commits verbatim into someone's codebase is exactly where a body the model never read cannot be checked), and attach-above-threshold with the tool result saying so. `Complete.report` is **deliberately excluded** — a bounded structured object, not a blob; a ref there would be a second way to say one thing
- **A closed `refusal` vocabulary** (§2b) — ten codes, every one enumerating a degradation that already exists (`anchor-not-commentable`, `suggestion-unsupported`, `git-write-blocked`, `edit-match-not-unique`, `ref-unauthorised`, `payload-spilled`, …). Modelled on `artifact-components`' publish verifier, which states a *security policy* as an error catalogue a model can program against. Three governing rules: closed set versioned with the tool surface (an open string field becomes a second, worse prose channel); **a code names what the harness did, never what the model should do next**; and no `ok` code, so "did this run hit any degradation" is a field test rather than a text search. The prose stays — it is what steers the model; the code is what `eval.md` counts and `memory.md` keys on
- **The `implement` completion gate gets a computed half** (§2c) — it was deterministic in *firing* and entirely prompted in *content*. Six of its checks are arithmetic the harness already holds state for (out-of-scope paths, writes outside the tree and scratch, scratch paths referenced from tracked files, placeholder tokens in **added lines only**, verification commands claimed but never executed, conventions-file edits), split FAIL/WARN. Four properties carried over verbatim from `dataviz`'s `validate_palette.py`: severity separates compensable from non-compensable, the block **states what it did not check**, no model call (the gate's whole argument, per SWE-agent's `review_on_submit_m`, is that a mechanical gate cannot be talked out of firing), and the check is scoped to what the decision turns on. Trigger, reset rule and status semantics unchanged
- **`AskUser` becomes a decision record** (§2d) — options become `{id, label, implication?}`; `<resumed_answer>` gains `option_id` and a three-value `match` enum (`exact`/`inferred`/`none`) with the reply text still carried verbatim; plan-mode questions may carry `draft_ref`. The `workshop` skill's structural claim is that **the question and the answer share a schema**, so the resume path never interprets prose. `match="none"` is the valuable value, not `exact`: it detects the non-answer `formats.md` §5 already anticipates ("a non-answer, a deflection, a reply that raises a new question") but currently leaves Forge to spot by reading. `draft_ref` is the `workshop` lesson proper — a human asked "online or offline migration?" *with the seven-step plan attached* answers a much better question than one asked cold
- **A fifth rule for `context-files.md` §12** (§2e) — a skill's instructions are read; its code is **executed and never `Read` into context**. `webapp-testing` states it directly ("black-box scripts rather than ingested into your context window") and the `pptx` skill's ~1.1 MB of ISO-IEC 29500-4 XSD and ~875-line validators is the evidence that a skill's size is only irrelevant to its context cost if the rule holds. With the corollary that makes it safe rather than merely cheap: an executable invoked without reading is a trust decision, so §12's provenance rules apply to the binary, not just the prose
- **One roadmap promotion with a named trigger** (§4) — a `Publish` tool and one page type, a review briefing, for which `artifact-pr-review` is a worked instance. Not v1 because the need is visible but not present; the trigger is stated so it can be *recognised* rather than argued: the first deployment where review output is read somewhere other than the PR. Four things already decided if it ships, including template-fill's non-obvious half (**creation-only** — "don't re-read or re-apply this template", which is what stops an edit silently reverting a customised page) and the honesty rule to copy verbatim: "the page must never present inferred state as computed state"
- **Three `future.md` items** (§5) — the MCP Apps `content`/`structuredContent` split, blocked on the version ceiling `adk.md` §0 already measured (ADK-Java pins MCP SDK `1.1.2`; no `MCP_2026_07_28` constant exists in the Java SDK at all), though `visibility: ["app"]` is worth stealing now and free to state; a local preview before an outward write, moving when `eval.md` shows Markdown→ADF conversion failures are real rather than theoretical; and the verified-lane/free-lane split with its cost priced
- **Four rejections with reasons** (§6) — in-band delimiter grammars (payload charged to context twice; the grammar is load-bearing enough that LibreChat ships a *"Common mistakes to avoid"* block to its OpenAI-family models and not its Anthropic ones; failure renders half an artefact instead of erroring); `canvas-design`'s fabricated user turn (the observation is right — a one-pass generative agent stops at "acceptable" — but the transcript is evidence a human reads and the ledger stores, and §2c's gate gets the same result honestly); a diffusion-model image tool (everything Forge could want to draw is *information*, not *content*, so the route is code and `Bash` already is it); and per-page-type skills as a v1 structure
- `agent-design/README.md` — six decision rows and the reading-order entry. **Two supersessions recorded rather than edited in place**, per the folder's own maintenance rules: `AddComment.body`-always-required, and `formats.md` §5's bare-text `<resumed_answer>`
- `agent-generative-output.md` §13 — marked settled and **left unedited** as the pre-decision shortlist, per the alternatives-are-recorded-never-invented rule. A shortlist rewritten after the fact reads identically to a real one

A separate pass the same day, on a different source: **Codex CLI, re-read at `ee6814b`** six months on from the last full pass. It found a different architecture rather than a newer version of the old one, which is why the entries below supersede parts of several docs rather than only adding to them.

- **The prompt corpus is no longer source.** Codex CLI does not compile a prompt file per model any more. The corpus lives in `codex-rs/models-manager/models.json` — nine models, each carrying its own `instructions_template` plus per-subsystem prompt fragments (`approvals`, `collaboration_modes`, `auto_review`, `multi_agent`, `permissions`, `token_budget`, `guardian_v2`, `confirmation_policies`, `persistent_instructions`) — served from `/models` and cached for **300 seconds**, with an `include_str!`-ed copy in the binary as the offline floor. So the deployed system prompt is a cached remote resource on a five-minute TTL: the committed text is what a client falls back to, not what a session ran on, and a prompt edit reaches every running client inside the TTL without a client release. `minimal_client_version` gates the other direction. New: `codex/model-catalog.md`
- **And the assembled prompt is a diff stream** — of *delivery*, not of authorship: the per-model instruction blob is a constant string (`get_model_instructions` returns `template.clone()`, its `personality` argument is ignored, and the doc comment reads "`instructions_template` is literal text"), with exactly one programmatic transformation applied to it, a subtraction of the planning section by heading match when `update_plan` is disabled. What is programmatic is which blobs appear. Sixteen named world-state sections (`ModelInstructionsState`, `AgentsMdState`, `PermissionsState`, `CollaborationModeState`, `PersistentModeState`, …) each implement `render_diff(previous)` against a SHA-1'd snapshot of their own prior value and **return nothing when unchanged**. A stable section costs zero bytes after its first turn; a changed one has to **revoke its predecessor by name**, because the old text is still in the transcript — `ext/git-attribution` is the honest illustration, rendering "Ignore any earlier instructions requiring Codex attribution" when the policy flips. Each section also carries a `with_legacy_matcher` so a resumed session can recognise and supersede fragments written in an older format: the prompt format is versioned *in the transcript*
- **`gpt-6-astra` is the first model here whose whole tool surface is one tool.** `tool_mode: "code_mode_only"` (the enum is `Direct | CodeMode | CodeModeOnly`, set per model by the catalog) collapses the registry into a single `ToolSpec::Freeform` carrying a **Lark grammar** — so constrained decoding, not JSON-schema validation, enforces the dialect — whose *description* absorbs every nested tool as a TypeScript signature grouped by namespace. The V8 isolate has **no ambient authority at all** ("no Node, no file system, no network access, no console"), so every effect routes back through the ordinary dispatcher and therefore back through sandboxing and approvals: the opposite answer to CodeAct+Hyperlight's containment, and the only one where a composition layer cannot widen the agent's permissions by existing. Two axes scored independently then crossed into an outcome matrix; truncation treated as omitted-not-benign without raising risk; prompt injection requiring affirmative evidence on two conjuncts; post-denial re-approval bounded at `critical`; "Prior Guardian decisions are context, not precedent"; and — **correcting this collection's previous claim** — a failed review returns to the human-approval path rather than resolving to rejection, with three distinct messages to the agent for a rejection, a failure and a timeout. Fifth pass: a one-line question — "if it's nonce wrapped then how could someone forge it?" — caught a wrong claim of mine and, following it, a real defect in the design.

- **The claim was wrong.** I had described `agent-design/context-files.md` as nonce-wrapping the conventions corpus "without escaping it, so the forged-envelope hole stays open." It isn't open: the run nonce makes forging a delimiter unrepresentable, which the doc itself already said in the sentence "a nonce makes the class unrepresentable rather than unlikely." The error was only ever in conversation, not in a committed file
- **The defect was real.** `context-files.md` §4's prose said *"The closing tag carries a nonce; the opening tag does not"* and called the scheme asymmetric. Three things in the design already said otherwise: the template printed directly above that sentence (`<conventions … nonce="{{nonce}}">`), the `<existing_comments>` precedent it cited as its model (`<existing_comments nonce="…">` … `</existing_comments nonce="…">`), and the shipped reviewer-core prompt, which promises the model a nonce *"you can see on both the opening and closing tag"*. Corrected in place with the supersession noted, per the folder's own maintenance rules — the mechanism never changed, only its description
- **Why symmetry is load-bearing here specifically**, now written down: in a single-envelope scheme the closing tag is all an attacker needs, because escaping the block is the whole attack. In a **multi-tier** envelope the attributes carry privilege — `binding="policy"` means non-overridable — so a body able to mint a plausible higher-binding *open* tag would not need to close anything, only to have the next paragraph read as org-level policy. The nonce on the open tag is what makes that unrepresentable
- New **§4a, what the nonce does not cover**, because "it is nonce-wrapped" is easy to hear as "it is handled". Covered completely: forging either delimiter. Not covered: characters that change what a *human* sees without changing what the model receives — bidi overrides, zero-width joiners, homoglyphs — since the body is injected verbatim and `formats.md` §1's sanitiser deliberately exempts repository file contents to keep `Edit`'s exact-match contract. That residual matters more here than anywhere else because of the **trust model**, not the mechanism: the repo tier is followed because a human reviewed and committed it, and an invisible-character payload attacks exactly that. Review mode is already hardened against the timing version (base SHA; a diff touching a conventions file is a finding) and neither rule helps against a payload that was invisible when approved
- **And escaping is the wrong fix, which reverses how it was first offered.** Once both delimiters carry a nonce it buys nothing against forgery, and it costs accuracy on a document that is full of angle brackets in generics/JSX/HTML examples and that the model is meant to quote from. Where OpenClaw actually points its own escaper is the tell: sub-agent results, attachments, operator focus text — payloads to be *treated as data*, never documents to be *followed*. The proportionate fix for the real residual is a **refusal at resolution time** (a section carrying invisible characters outside a code fence fails resolution and the run does not start) rather than a transformation, keeping the never-transform rule and the byte-identical-to-disk guarantee intact. Not v1

Sixth pass: three answers folded, then a seam pass over `agent-design/` — the thing earlier passes found most defects in. It found nine, six of them introduced by this session's own additions.

- **The collision I introduced, resolved, and it improved the rule.** Adopting the persistence rule and `budget_exhausted` in one pass left a run that is blocked once *and* out of budget with two contradictory instructions. `budget_exhausted` now wins, and the obstacle goes in the report body. The consequence is the interesting part: the ledger retries with a raised budget, the retry's envelope carries the previous attempt's report verbatim, and an obstacle named there **counts as the first occurrence** — so the persistence rule spans *attempts* rather than turns. That is where it belonged, because a second look at an obstacle is only worth having if it gets a real context window, and the within-a-run version guaranteed the opposite. Bounded by `max_attempts: 2`, so a task that exhausts context twice is abandoned rather than raised a third time
- **Suppressed depth-0 spinoffs need no machinery** — `outcome.report` already stores the completing run's report verbatim and `spun_off` is part of it, so the dispatcher simply declines to act on the entries. They reach a human by paths that already exist: a `blocks_this`-shaped overflow lands the task in `blocked`, which §10 projects, and a `follows_this`-shaped one completes so the report reaches the ticket. The gap only looked real because §11 and §2 were written in different passes
- **The invisible-character check becomes v1**, overturning my own not-v1 call. A resolution-time **refusal**, not a transformation: a section carrying `Cf`/`Cc`/`U+2028`/`U+2029` outside a fenced code block fails resolution, and §1b's existing rule means the run does not start. It preserves every guarantee (never transform, byte-identical to disk, `Edit`'s exact-match contract) because nothing is rewritten, and it fails toward the *right* human — the attack works by making a reviewer see something other than what the model gets, so the mitigation has to end at a reviewer. Fenced blocks are exempt, because a conventions file may legitimately contain examples about Unicode handling and a rule that cannot say so is a rule teams disable. Accepted cost stated rather than discovered: a stray soft hyphen from a word processor stops every run against that repository until someone removes it

The seam pass, and what it caught:

- **A capability advertised with no result-side signal.** `Read` gained `char_offset` last pass, but `formats.md` §8b never described a clamped line — its cap vocabulary covered the line window and the byte ceiling, both of which resume on the *next* line, and a clamped line has no next line. So `clamped` is now a distinct status with its own note (`line 1 clamped at 2000 chars — pass char_offset: 2000`), distinct from `truncated` precisely because a `truncated` note tells the model to advance `start_line`, which on a one-line minified file advances past the whole file. Without it, `char_offset` was a parameter nothing would ever tell the model to reach for — the exact failure the collection keeps documenting
- **`blocked` had acquired two new origins and its description still named one.** `tools.md` said "within a single run, use AskUser directly instead of reaching Complete with status `blocked`" — true before this session, false after it, since a `blocks_this` spinoff and a satisfied persistence rule are both legitimate in-run routes to `blocked`. - **Read-only runs do not occupy an owner.** The naive reading of the task record — every task has an `owner`, therefore every task competes — would serialise `plan` runs behind implementation on (repository, branch), and the failure that produces is a quiet throughput collapse nobody diagnoses. - **Plan mode was being told to use the wrong field.** The new file-it-don't-do-it section applies to the whole coding prompt, but a `plan` run does nothing by construction, and the plan schema already has `out_of_scope` for exactly this. Seventh pass: the reconciliation pass `orchestration.md` §10 had been carrying as its one open item. Two reframings did most of the work.

- **It is not a sync problem.** The instinct on two stores that can disagree is bidirectional sync — detect divergence, merge, resolve. That turns a small problem into a distributed-systems one, and it is wrong here: the two stores hold **disjoint field sets**. The tracker owns intent (should this happen, for whom, how important, what does done mean); the ledger owns execution (has a run started, what did it produce, which branch is bound, how many attempts remain). Nothing is authoritative in both places, so there is no symmetric conflict to merge — only **a tracker change that invalidates an execution assumption**. That reduces reconciliation from sync to *invalidation*: you do not merge two versions, you notice a premise changed and either re-derive or stop. Same shape as the context service's cache design, and it should be, because the ledger's copy of a ticket **is** a cache
- **Three verbs, and the constraint that produces them.** The ledger cannot write to the tracker — `AddComment` is the only outward channel, `WriteJira` is deferred — so every reconciliation action is **adopt**, **stop**, or **say**. It can never *fix*. A permissions decision made for unrelated reasons turns out to make reconciliation tractable: with three verbs there is no reconciliation logic to get subtly wrong, and every branch's failure mode is "a human is told"
- **It runs at transitions, not through a watcher**: a ticket re-read before dispatch and at settlement, plus an opportunistic sweep for non-running tasks. §8's argument in a new place — a watcher must be running, can silently stop, and reasons over what it happens to be shown, where a check at a transition is a query that either ran or did not. A tracker-event subscription is a latency optimisation on top, so without it reconciliation is *late*, not absent
- **The eleven-row case table**, with four reasons stated. **Closing a ticket does not delete the work**: a `running` task that finishes after its ticket closed leaves a branch with real commits, so the projection carries `outcome.target_branch` and the managed-worktree lossless-only rule keeps the checkout — otherwise the ledger knows where the work is and the only person who could use it does not. **Reopening produces a new task with `supersedes`**, not a resurrection, because resurrection forces a choice between resetting the attempt budget (losing the give-up signal) and keeping it (re-abandoning immediately). **Stale requirements earn the fifth projection**, and the contrast with last pass's depth-0 overflow decision is the point: the same test — *is this fact anywhere a person will already be looking?* — gives opposite answers, because a report reaching the ticket cannot mention that the ticket moved under it. **An undeliverable projection is not nothing**, so a failed `AddComment` is recorded against the task and surfaced on the run record; a projection layer that treats undeliverable as done reintroduces exactly the silence §10 exists to prevent
- **Reassignment mid-`handoff` turned out to be a no-op**, which is evidence rather than luck: under the earlier `(repository, ticket assignee)` key it was a real case with no clean answer, and keying on `(repository, branch)` deleted it. A key change removing a whole row from the reconciliation table is the usual sign the key was named after the wrong thing first time
- Two anti-loop rules — **the ledger ignores its own projections** (arriving here before the PR steward that will need the same rule) and **one observation, one action** via `tracker_observed.revision`, so a change is reconciled once even if several passes see it
- Two things left open and named: **multi-ticket tasks** (a human splitting or merging tickets produces a shape one `issue_key` cannot represent; the degenerate handling is honest but crude), and the fact that **the tracker's `done` and the ledger's `done` are different claims** — fine while `AddComment` is the only write, a real decision the moment `WriteJira` lands
